# Implementation plan — signup, roles and access

Written 29 Sep 2026, after the Sep 22 review call. Supersedes the open questions in
`FEEDBACK-2026-09.md`, which stays as the comment-by-comment record.

**Fixed point:** ASCRS Foundation presentation, **8–9 October**. Anurag needs a slide of the
platform's look and feel. That is what splits phase 1 from everything else: phase 1 is only what
shows up in a screenshot, and it carries no data risk beyond one enum rename.

**Decisions this plan is built on**

- `admin` → **Super User** (us, whole platform). `residency_administrator` → **Program
  Administrator** (one institution).
- The **personal email** is the account's anchor: always required, always editable, survives
  graduation.
- The **institutional email** is required for every role where the institution is required —
  trainees and program administrators. Optional for attending physicians, who may stay unaffiliated
  with the core curriculum only.
- Requiring an institutional address is *not* requiring a known domain. An address on a domain we
  have never seen is accepted; it simply does not auto-validate, and a Program Administrator at that
  institution approves it.
- A user keeps access to the local content of **every** institution they have ever been affiliated
  with.

# Phase 2 — the identity model

The structural work. About a week. Nothing here shows in a screenshot, which is exactly why it waits
until after the 8th.

## 2.1 Affiliations become a table

New `user_affiliations`: `userId`, `institutionId`, `institutionalEmail`, `emailVerifiedAt`,
`validationStatus`, `validatedById`, `validatedAt`, `note`, `startedAt`, `endedAt`.

The migration backfills one row per existing user from `users.institutionId` and `users.email`.

`users.institutionId` stays as a denormalised pointer to the *current* affiliation, so the existing
queries keep working and can be migrated one at a time rather than all at once.

Access rule: a user sees the local content of every affiliation they hold, current **or** ended.

## 2.2 Flip the email model

- `users.secondaryEmail` becomes `users.personalEmail`: **required**, unique, editable, and the
  address every recovery and notification goes to.
- `users.email` (the institutional one) moves onto the affiliation. A person may hold several.
- Domain matching runs against the affiliation's address, not against `users.email`.

**Migration decision.** Existing accounts mostly have no personal address. Rather than invent one,
add a `PENDING_PERSONAL_EMAIL` status and reuse the `ProfileCompletionGuard` pattern: on next sign-in
the person is pinned to a one-field screen until they give one. It is the same machinery as
`PENDING_PROFILE`, so it is cheap and it never guesses at somebody's address.

**Signup, after the flip**

| Role | Institution | Institutional email |
| --- | --- | --- |
| Medical student / Resident / Fellow | required | required |
| Attending physician | optional | optional |
| Program Administrator | required | required |
| Super User | n/a | n/a |

## 2.3 Profile rework

Membership becomes: Username *(fixed)* · Personal email *(editable)* · Institutional emails *(a list,
add and remove)* · Current institution · Member since — and a separate **Past affiliations** block.

# Phase 3 — permissions

Two to three days, and it depends on phase 2 only for the "which institution" question.

- `assertCanReview`: a Program Administrator may validate **anyone** whose institution is theirs —
  trainees, attending physicians asking for affiliation, and other program administrators. The Super
  User keeps global scope.
- **First-administrator rule:** a Program Administrator at an institution that has no validated
  administrator yet can only be approved by a Super User. Everybody after that is approved locally.
- Validate dialog: no institution picker for a Program Administrator; keep it for the Super User.
- **People** is scoped to their own institution for a Program Administrator. It currently shows
  everybody on the platform.
- Extend the service specs — the existing ones already cover the unvalidated-reviewer case.

---

# Phase 4 — notifications

- Email the user when their account is accepted. Small; the Gmail sender already works.
- Email the administrator when a request arrives, and again after about a week. The reminder needs a
  scheduler — Cloud Scheduler hitting an authenticated endpoint is the least new machinery.
- In-app: a pending-work indicator in the header. `countPendingValidation` already exists.
- Accept-or-decline straight from the email: a signed single-use token. Worth doing, not first.

---

# Phase 5 — core vs local lectures

Not onboarding, and it deserves its own design pass. But one decision is needed earlier than the rest
of it, because phase 1's copy claims an unvalidated user can already watch things: **a lecture needs a
scope** (`core` or `institution`, plus an `institutionId` for the latter), and promoting a local
lecture to core is gated to a Super User.
